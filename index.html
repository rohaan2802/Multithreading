Overview

The brief is a revision of POSIX threads and performance, for Parallel and Distributed Computing at FAST-NUCES, Spring 2026 (roll 22I-2327, section F).

V1

Serial baseline

A single-threaded implementation of each kernel. This is the correctness reference and the T1 in every speedup figure.

V2

Pthreads, OS scheduling

Work is split into chunks and picked up by a pool of threads. The operating system places those threads on cores; there is no manual affinity.

V3

Affinity and static chunks

Each thread is pinned with pthread_setaffinity_np and walks a static set of chunks (tid, tid+T, tid+2T, …).

Report

Measurement

Runtime, speedup and efficiency at 1–4 threads, on 10%, 50% and 100% of each dataset, five trials each. V3 is also profiled with gprof.

The Three Workloads

Three problems with different memory behaviour, each in three versions. Only C and Pthreads are used — no OpenMP, TBB or std::thread.

Task 1SUSY logistic scoringDense, compute-bound · 18 features + a fixed bias▾

Each row of the SUSY CSV is a label followed by 18 numeric features. A fixed logistic model (bias −0.35 and a given weight vector) produces a probability; records with p ≥ 0.5 are predicted positive. The program prints N, PRED_POS, TP, FP, TN and FN.

  • task1_v1_serial.c
  • task1_v2_pthreads.c
  • task1_v3_affinity.c
  • gprof_task1_v3.txt
  • results/task1.xlsx
Task 2Sparse matrix–vector multiplyCOO → CSR, then y = Ax on webbase-1M▾

The SuiteSparse webbase-1M matrix is a 1,000,005 × 1,000,005 web graph with 3,105,536 non-zeros. After a CSR build (outside the timer), the programs compute y = Ax with x[j] = (j mod 1000) / 1000 and print a checksum. A correct full run gives CHECKSUM 499500.015000. Parallel versions split work on row chunks.

  • task2_v1_serial.c
  • task2_v2_pthreads.c
  • task2_v3_affinity.c
  • gprof_task2_v3.txt
  • results/task2.xlsx
Task 3BFS on a web graphSNAP web-Google, source 0▾

SNAP’s web-Google graph has 875,713 nodes and 5,105,039 directed edges. BFS from node 0 reaches 600,493 of them; the farthest sits at hop-distance 32. The programs print the reachable count, the maximum distance, and a per-level histogram. This kernel is the hardest of the three to scale, because of frontier synchronisation and irregular neighbour walks.

The best average speedup is about 2.1×, on Task 2 with three V2 threads. Four threads share two physical cores, and efficiency falls off. BFS is the awkward case: a second thread can be slower than the serial code, and even the best figure is only about 1.5×. gprof puts 98% of Task 1 inside worker_v3, and most of Task 3 inside bfs_worker_v3; Task 2 shares time between the worker, the driver and the matrix reader.

How to Compile and Run

Linux or WSL, with GCC. Version 3 uses pthread_setaffinity_np, which is a GNU/Linux extension.

Clone the repository

bash
git clone https://github.com/rohaan2802/Multithreading.git
cd Multithreading
bash scripts/extract_datasets.sh
make

Run a program

bash
./bin/task2_v1_serial datasets/webbase-1M.mtx
./bin/task2_v2_pthreads datasets/webbase-1M.mtx 4 1024
./bin/task2_v3_affinity datasets/webbase-1M.mtx 4 1024

./bin/task3_v1_serial datasets/web-Google.txt
./bin/task3_v2_pthreads datasets/web-Google.txt 4 2048
./bin/task3_v3_affinity datasets/web-Google.txt 4 2048

./bin/task1_v1_serial path/to/supersymmetry_dataset.csv
./bin/task1_v2_pthreads path/to/supersymmetry_dataset.csv 4 200000
./bin/task1_v3_affinity path/to/supersymmetry_dataset.csv 4 200000

Task 1 needs the SUSY CSV, which comes from release/SUSY.zip or from the UCI SUSY page. A longer walkthrough, including a gprof example, is in the README.
